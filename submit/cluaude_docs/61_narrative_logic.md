## 1. ナラティブの5段階+1構成

| 幕 | トリガー | 距離 | 文字上限 | 表示位置 | 目的 |
|---|---|---|---|---|---|
| **Act 0** | QRスキャン（B②入口） | 任意 | 80字 | 全画面モーダル | 「行きたい」動機の生成。問いを渡す、答えは出さない |
| **Act 1a** | GPS 300m圏内検知 | 300m | 60字 | バナー通知 | 時代・人物・文脈の断片。期待値を上げる |
| **Act 1b** | GPS 100m圏内検知 | 100m | 50字 | バナー通知 | 未解決の問い＋現地手がかり。関心曲線の最高点直前 |
| **Act 2** | GPS 50m圏内検知 | 50m | 30字 | バナー通知 | 現実との接続。行動誘発で終わる |
| **F7断片** | 押印セレモニーF7（0.6〜1.2秒、自動） | 0m | 30〜40字 | セレモニー画面 | F7全文の冒頭1文。好奇心維持 |
| **F7全文** | ポストスキャンカード（ユーザーペース） | 0m | 120字 | カード本文 | Act 1bの問いへの答え＋次スポット引力 |

## 2. 関心曲線の設計

B09「関心曲線のレンズ」適用。

```
関心
  ↑
高│                      ★押印（ピーク）
  │                    ╱│╲
  │               Act2╱ │ ╲F7断片（余韻）
  │            Act1b╱   │   ╲___F7全文（解決＋次への上昇）
  │        Act1a╱        │
  │    Act0╱              │
低│  ╱                    │
  └─────────────────────────→ 時間
```

各幕がユーザーの関心を段階的に押し上げる設計。**Act 1b で「問い」をMAX、押印で「解決」、F7全文で「次への引力」** の3拍子。

---

## 3. コンテンツルール（必須）

| ルール | 理由 |
|---|---|
| 固有名詞（地名・人名・年代）を必ず含める | リアルとの接続が消えると物語にならない |
| Act 1b〜Act 2: 現地で確認できる物理的手がかり | 「見える・触れる」を入れる |
| F7全文: Act 1bで渡した問いへの答えを必ず含める | 関心曲線の収束点 |
| F7全文: 最終スポット以外は次スポットへの引力で終わる | コアループ継続の動機 |
| 史実確認: 一次ソースで必ず確認 | AI生成史実をそのまま使用しない（信頼性の根幹） |

## 4. クライアント側 GPS 監視ロジック

### 4-1. ポーリング戦略

```typescript
// 進行中ルートあり、かつ次スポット未押印の場合のみ起動
if (currentRoute && nextSpot) {
  navigator.geolocation.watchPosition((pos) => {
    const d = haversine(nextSpot.location, pos.coords);

    if (d <= 300 && !shownAct1a) {
      showBanner('act_1a', nextSpot.narrative.act_1a_text);
      shownAct1a = true;
    }
    if (d <= 100 && !shownAct1b) {
      showBanner('act_1b', nextSpot.narrative.act_1b_text);
      shownAct1b = true;
    }
    if (d <= 50 && !shownAct2) {
      showBanner('act_2', nextSpot.narrative.act_2_text);
      shownAct2 = true;
      enableStampButton();
    }
  }, null, { enableHighAccuracy: true, maximumAge: 5000 });
}
```

### 4-2. バナー表示の重複防止

各スポット × 各幕 = 1回のみ表示。ローカルストレージに `shown_acts[spot_id][act]` を記録。

ただし **押印未完了の同一スポットへの再接近時は表示**（離脱→再訪のケース）。

### 4-3. バックグラウンド時

OSプッシュ通知に切り替え（FCM経由）。前景時はアプリ内バナー。

## 5. データ取得タイミング

### 5-1. ルート開始時

`GET /routes/{id}` で **全スポットの narrative_fragments を一括取得**。

理由: 圏外でもナラティブが表示できるよう、クライアント側にキャッシュ。

```typescript
{
  route: { /* ... */ },
  spots: [
    {
      id, name, location, sequence, is_final,
      narrative: {
        act_1a_text, act_1b_text, act_2_text, f7_fragment, f7_full
      }
    },
    ...
  ]
}
```

### 5-2. Act 0

`POST /triggers/{qr_token}` で取得。Act 0 は **そのトリガーQRから起動した場合のみ表示**。マップ経由でルート開始した場合は表示しない（任意性）。

### 5-3. F7断片・F7全文

押印 API（`POST /checkin`）のレスポンスで取得。事前キャッシュは行わない（押印前にネタバレ防止）。

## 6. 史実確認プロセス

ナラティブ制作時の必須プロセス。

```
1. 一次ソース（自治体公式・図書館郷土資料・学術論文）で事実確認
2. ソースのURL or 書誌情報を narrative_fragments.source_refs (JSONB) に記録
3. 編集者（運営）レビュー → 公開フラグ ON
4. ユーザーから誤り報告があった場合の修正フロー（Phase 2）
```

`narrative_fragments` に `source_refs JSONB` カラムの追加を [30_data_model.md](./30_data_model.md) に反映する（Phase 1のスキーマ初版で含めるかは Owner決裁）。

## 8. ナラティブ品質基準（チェックリスト）

PR提出前に編集者がチェック:

- [ ] 固有名詞（地名・人名・年代）が含まれているか
- [ ] Act 1b〜Act 2 に現地で確認できる物理的手がかりがあるか
- [ ] F7全文が Act 1b の問いに答えているか
- [ ] 最終スポット以外、F7全文が次スポットへの引力で終わっているか
- [ ] 最終スポットのF7全文が「完結の余韻」で終わっているか
- [ ] 史実が一次ソースで確認されているか（source_refs記録）
- [ ] 文字数上限を超えていないか（80/60/50/30/40/120）

## 9. ナラティブの編集権限

| Phase | 編集主体 | ツール |
|---|---|---|
| Phase 1 | 運営（コアチーム） | Retool（簡易CMS） |
| Phase 2 | 運営 + 施設（A③イベント時） | Retool |
| Phase 3〜 | 運営 + 施設 + 自治体 | パートナーポータル（新規開発） |
| Phase 4〜 | ユーザー（独自ミッション作成） | UGC機能 |
| Phase 5〜 | 完全プラットフォーム化 | — |

Phase 1 MVPでは **運営代行のみ**。CMSのUIは Retool で組む（自社開発しない）。

## 10. ナラティブ表示の i18n / 多言語対応

Phase 1 MVPは **日本語のみ**。

ただしDB設計では将来の多言語化を想定:
- `narrative_fragments` のテキストカラムを別テーブル `narrative_fragment_translations` に分離する設計を検討
- Phase 1 では単一カラム維持、Phase 3〜で分離マイグレーション

英字サブタイトル（称号）はMVPから併記済み。
