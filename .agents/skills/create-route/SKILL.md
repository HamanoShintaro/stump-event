# SHUIN ルート作成スキル (`create-route`)

このスキルは、駅やエリア名・テーマから **「①史実・実在スポット調査＆ドラフト作成 → ②ハルシネーション・住所・電話番号・緯度経度の厳密検証 → ③OpenAIモデルによる画像生成 → ④Supabase非破壊UPSERT＆`mock.ts`反映」** までを一気通貫で実行するための標準ランブックです。

---

## 事前確認: OpenAI APIキーの安全な確認（Safe Credentials Protocol）

Step 3 で OpenAI の画像生成モデルを使用するため、作業開始時に `OPENAI_API_KEY` が `.env.local` または `~/.env` に設定されているか確認します（キーの値は絶対に出力しないこと）。

```bash
grep -sq "^OPENAI_API_KEY=" /Users/shintaro/stump-event/.env.local || grep -sq "^OPENAI_API_KEY=" ~/.env
```

- **終了コードが 0 以外（未設定）の場合**:
  画像生成ステップに進む前に、ユーザーへ以下のコマンドをターミナルで実行してキーを登録するよう案内してください（チャット欄へ直接貼らせないこと）：
  ```bash
  printf "Enter OPENAI_API_KEY (typing hidden): " && read -s val && echo && echo "OPENAI_API_KEY=$val" >> "/Users/shintaro/stump-event/.env.local" && echo "Saved."
  ```

## Step 1: 一次情報のWeb調査とエリア定義（`scripts/areas/<slug>.mjs`）の作成

**⚠️ 最重要原則: 記憶や推測でスポット名・住所・電話番号・緯度経度・歴史年号を書かないこと。**

1. **実在スポットと史実のWeb検索（`search_web`）**
   - 対象エリアの歴史・伝承・地形の一次情報／公的資料／信頼できる出典を `search_web` で調査します。
   - ルートを構成する **5つのスポット** を選定し、各スポットについて以下を必ず `search_web` で裏取りします：
     - **実在確認・営業状況（2025〜2026年 閉店ネガティブ検索の義務化 / 処方箋57）**: 古い観光記事や食べログまとめに残っている店舗が直近で閉店しているケースを防ぐため、必ず **`"<店名>" "<駅名または自治体名>" 閉店 OR 閉業 OR 移転 2025 OR 2026`** でネガティブ検索を行い、現在も営業中であることを確認すること。
     - **正確な住所（都道府県・市区町村・丁目・番地・号まで）** ※「〜周辺」などの曖昧な住所は禁止
     - **電話番号（店舗等で記載する場合）** が実在の公式情報と一致しているか
2. **ルート構成ルール（[docs/templates/route_input_v2.md](../../docs/templates/route_input_v2.md) 準拠）**
   - **禁止用語の厳守**: ユーザー向け文言に「スタンプラリー」「ラリー」「ナラティブ」「スタンプ」「挑戦する」「クリアする」は絶対に使わない（「ルート」「物語」「しるし」「押印」「SHUIN」「めぐる」「巡る」を使用）。
   - **駅そのものをスポットにしない原則（実質4スポット化の防止）**: 鉄道駅（〇〇駅）はあくまで散策の出発・到着拠点であり、旧田園調布駅舎のように駅舎自体が独立した文化財・観光目的地となっている特例を除き、**5つのスポットに「〇〇駅」自体を含めないこと**（スタート地点を駅にしてしまうと実質4スポットのルートになってしまうため、必ず街の中の寺社・史跡・公園・文化施設・店舗など5つの実在スポットで構成する）。駅の開業史や駅名の由来はルートの `description` や第1スポットの導入（`clue`）に織り込むこと。
   - **タイトルの多様化ルール（「なぜ〜のか」の一律連発禁止）**: ルートの `title` がすべて「なぜ〜のか——…」から始まるワンパターンにならないよう、街の個性やテーマに合わせて以下のように切り口を多様化すること（「なぜ〜」型は複数ルート作成時も全体の1〜2割以下に抑える）：
     - **情景・五感型**: 「坂の上の焼きたてパンと珈琲の香り——…」「鉄橋を渡る電車の音と、川風のテラス——…」
     - **時間・歴史紀行型**: 「三蔵法師が辿り着いた丘——…」「縄文の海辺から『豊かな春』へ——…」
     - **対比・発見型**: 「未来都市の足元に息づく400年の街道——…」「タワマンの隣に残る手仕事の温度——…」
     - **象徴モチーフ型**: 「寺が消えても咲き続ける千年の紫——…」「黒湯の記憶と幻の日月桃——…」
     - **⚠️「——〔駅名〕、」および「読点（、）で2節に分ける30字タイトル」の連発禁止（処方箋㉙）**: すべてのタイトルを「AとB——〔駅名〕、CとDをめぐる」や「AのB、CとDをめぐるX」（読点1つで前後2節に分ける構文）に揃えると金太郎飴感が出るため、バッチ内の半数以上（5駅中3駅以上）は**読点（、）を使わない短詩型タイトル（16〜23字）・小説の章題風・時間や音から始まるタイトル**にすること。
   - **徒歩動線・現地視覚物・脱テンプレの6原則（[references/feedback-log.md](references/feedback-log.md) 準拠）**:
     1. **一筆書き動線＆距離上限**: Spot 1は駅から徒歩3〜8分（直線500m以内）とし、駅をまたいで往復するジグザグ移動を厳禁とする（スポット間は原則直線850m以内、直線合計2.8km以内）。
     2. **「埋め戻されて今は何もない遺跡公園」の単体採用禁止**: 現地に行ったユーザーが顔を上げたとき、**今そこに目に見えるユニークな実体（建築・石仏群・展望・高低差・水辺・名物など）**がある場所のみをスポットにする。
     3. **「Spot 5＝洋菓子/カフェ」固定の廃止＆食体験スタイルの分散・カフェ重複禁止（処方箋㉚・㉝・㉟）**: カフェや食事をSpot 1〜3に置くルートや、序盤・中盤でテイクアウトして終盤のベンチで広げるルート（1バッチ最大1〜2駅まで）、店先の鉄板・蒸し器の前で熱々を味わうルート、最初に食堂・うどん店で腹ごしらえするルートなど、5駅すべてで食のタイミングとスタイルを変える。また**1ルートに喫茶・カフェを2軒重複させないこと**、ホット飲料等をテイクアウトしたまま30分歩き回らせる生理的矛盾を避けること。
     4. **4択（`question` & `choices`）の非テンプレ化（処方箋㉛）**: 「なぜ歴史と現代が共存しているのか？」や「〜を歩いて、あなたの心にいちばん深く残った〇〇はどれだろう？」という振り返りアンケート型の同一構文を全面禁止し、5駅すべてで異なる問いの切り口（帰りの車窓で最初に思い出す記憶は？／友人を一人案内するなら？／自分の街に持ち帰りたい知恵は？／過去の住人と目線が重なった場所は？／隠れた主役を一つ教えるなら？等）と異なる文末（`〜ですか？`/`〜ますか？`/`〜だろう？`/`〜だろうか？`）にする。また `rarity: 4` を選択肢Dに固定せずA/B/C/Dへシャッフル配置する。
     5. **五感のライブ感・年号ダイエット・`clue` 文字量の黄金比（処方箋㉕・㉞・㊱）**: 毎スポット「明治〇年（18XX年）創業」と書くのを禁止し、年号は1ルート最大3〜4回（または年号ゼロ）に絞る。また全5スポットの `clue` を一律100字前後に短文化（ダイジェスト化）するのを禁止し、**「1スポットは80〜110字の短い呼吸スポット」「主役となる2〜3スポットは180〜230字の濃密な五感描写」** の黄金比を守ること。さらにスポット順序調整後は `hook` の方角・徒歩分数が実座標間の計算値と一致しているか必ず確認すること。
     6. **`description` の行程目次テンプレ廃止＆ `surprise` 5スポット5様の文末＋ファクトの核（処方箋㉔・㉖・㉘・㉜）**: ルート `description` にSpot 1〜5を順番に並べる目次書きを禁止し、街の空気感や問いかけで引き込む導入にする。また `surprise` には単なる情景ポエムではなく**「現地で見た目だけでは分からない意外な事実・歴史の仕組み（Why/How）」を必ず含める**こと。文末に「〜こと。」やSpot 5での感傷的な推量語尾（「〜なのだろう。」「〜ことだろう。」）を使うのは禁止とし、「〜のだ。」「〜という。」「〜ている。」などの同一文末表現を1ルート内で2回以上繰り返すことも禁止する。
   - **回遊ルール（必須）**: 5スポットのうち最低1つは `spot_type` を `"買い物"` / `"休憩"` / `"食事"` のいずれかにする（他は `"見どころ"`）。
   - **物語の3要素**: 各スポットに `clue`（手がかり）、`surprise`（現地での発見）、`hook`（次スポットへの引き ※最終スポットは `""`）を設定し、最後に4択の `question` と `choices`（A〜D）へ収束させる。
3. **ファイルの保存**
   - `scripts/areas/<slug>.mjs` を作成します（参考実装: [scripts/areas/higashi_iwatsuki.mjs](../../scripts/areas/higashi_iwatsuki.mjs)）。

## Step 2: 座標の自動ジオコーディング校正 ＆ ファクトチェック検証ゲート

LLMが推測した緯度経度は100%ずれるため、**必ず以下の検証スクリプト＋独立サブエージェント検証**を通過させます。

### 2-1. ジオコーディング逆引き＆座標自動補正スクリプトの実行

Google Maps（施設名＋枝番・号まで一致した建物ピンポイント座標 / Rooftop精度1〜2m）、国土地理院（GSI）API、および OpenStreetMap（Overpass API）と照合し、スキーマ・禁止用語・住所番地・緯度経度のズレを検査＆自動補正します。

> **⚠️ 技術的注意点（国土地理院APIの限界とGoogle Maps Rooftop優先の理由）**
> 国土地理院の住所検索API（`msearch.gsi.go.jp`）は、住所の **「号（〇丁目〇番〇号の号）」や「枝番（1198-5の -5）」を切り捨てて、街区・親番の代表点（中心点）を返す仕様** になっています。そのため、広大な親番（例：`米島1198番地`＝駅線路から南口ロータリーまで広がる区画）では、国土地理院の座標を使うと実際の店舗から100〜200mずれてしまいます。
> [verify-and-geocode.mjs](scripts/verify-and-geocode.mjs) は **Google Maps の「施設名＋枝番・号」ピンポイント座標（Rooftop）を最優先の権威データ（許容誤差30m以内）** として使用し、食べログやGoogleマップのピンと1〜2m以内で完全一致させます。

```bash
node .agents/skills/create-route/scripts/verify-and-geocode.mjs scripts/areas/<slug>.mjs --fix
```

- `--fix` を付けると、設定された住所・POI形状から逆引きした正確な座標（国土地理院 / OSM Overpass）で `.mjs` 内の `lat` / `lng` を自動上書きします。
- 補正後、再度 `--fix` なしで実行し、**エラー0件**であることを確認します：
  ```bash
  node .agents/skills/create-route/scripts/verify-and-geocode.mjs scripts/areas/<slug>.mjs
  ```

### 2-2. 独立サブエージェントによるハルシネーション＆実在性ファクトチェック

スクリプトが出力する「📋 ファクトチェック対象一覧（`description` および `mock.ts` オーバーレイに入る `f7_fragment` / `f7_full` を含む全テキスト）」を対象に、`invoke_subagent`（`research`）を起動して第三者ファクトチェックを行います。

- **サブエージェントへの指示内容**:
  1. **歴史的情報の裏取り**: 年号、人物名、寺社や街の由来、4択の解説（`description`, `clue`, `surprise`, `f7_full`）にハルシネーション（事実誤認や架空の逸話）がないか `search_web` で1件ずつ検証すること。
  2. **スポット実在・住所・電話番号の裏取り**: 全5スポットの名称・住所（番地まで）・電話番号（存在する場合）が実在のものと完全一致しているか確認すること。
  3. **緯度経度の最終確認**: 補正後の `lat` / `lng` が実際の施設位置（押印半径50m圏内）と合致しているか確認すること。
- 指摘事項があれば `scripts/areas/<slug>.mjs` を修正し、再度 2-1 の検証スクリプトを通します。

## Step 3: ジャンル別ビジュアル生成 ＆ マルチモーダル自己改善エンジン（一括非停止生成）

> **🎨 最重要デザイン思想：なぜ「実写のネタバレ写真」や「均一な水彩ビネット」ではなく「10ジャンルの多様なイラスト表現」にするのか？**
> - 現地を訪れる前にリアルな実写全体像を見せてしまうと、現地に立ったときの感動が「未知の発見」から「写真の答え合わせ」へと目減りしてしまいます。
> - 一方で、全ルートに `"watercolor and ink"` や `"24% cream Washi margins"` を一律指定すると、一覧カードもスポット一覧も「白い楕円枠に浮いた同じ茶色いペン水彩」ばかりになり魅力が損なわれます。
> - そのため、クォータ停止の原因になる内蔵 `image-generator` サブエージェントは使用せず、**[generate-images-openai.mjs](scripts/generate-images-openai.mjs) と [style-genres.json](references/style-genres.json) による「10ジャンル自動分散 × スポット5段階カメラ分離 × Vision自動採点・自己改善」** でアイキャッチ＋スポット5枚（計6枚）を一括生成します。

### 3-1. エリア定義（`scripts/areas/<slug>.mjs`）でのプロンプト記述ルール
- **`eyecatch_prompt` および `spots[].image_prompt` には「純粋な被写体・モチーフ・季節・情景」のみを英語で記述すること**:
  - ❌ **禁止**: `"Daylight watercolor and ink illustration of..."` のような画材・昼間固定フレーズや、`"occupying only the central 42%/52% ... 24-percent unpainted cream-white Washi paper margins"` のような白い楕円余白指定は書かないこと（既存ファイルに残っている場合もスクリプト側で自動クレンジングされます）。
  - ✅ **推奨**: 割り当てられる10ジャンル（新版画・リソグラフ鉄道ポスター・厚塗りガッシュ・型染ちぎり絵・シネマティック逆光・鳥瞰アイソメ絵地図・岩絵具日本画・建築万年筆スケッチ・油彩インパスト・朝霧パステル）はスクリプトが `station_order`（または `style_genre` フィールド / `--genre` 引数）から衝突なしで自動適用します。
- **同一ルート内のスポット5枚は「5段階のカメラ距離・時間帯」に自動ロックされます**:
  - Spot 1: 広角アプローチ遠景（朝の斜光）
  - Spot 2: 建築空間と光影のミディアムワイド
  - Spot 3: 真上90度俯瞰フラットレイ／質感マクロ
  - Spot 4: ローアングル仰角／対角線奥行き構図（午後の陰影）
  - Spot 5: 夕景・マジックアワーの象徴的フィナーレ

### 3-2. 一括画像生成＆ジャンル別自己改善の実行（Codex サブスク枠・API課金ゼロ対応）
```bash
# 標準実行（ローカル Codex CLI / ChatGPTサブスク認証を自動検出し、アイキャッチ1枚＋スポット5枚を生成＆Vision採点・ジャンル学習）
node .agents/skills/create-route/scripts/generate-images-openai.mjs scripts/areas/<slug>.mjs --force

# プロバイダを明示固定する場合（codex | openai | gemini | auto）
node .agents/skills/create-route/scripts/generate-images-openai.mjs scripts/areas/<slug>.mjs --provider codex --force

# ジャンル一覧と各ジャンルの自己改善スコア・バージョンを確認
node .agents/skills/create-route/scripts/generate-images-openai.mjs --list-genres

# 特定ジャンルに対して人間のフィードバックを反映し、そのジャンルだけを進化させる場合
node .agents/skills/create-route/scripts/generate-images-openai.mjs --evolve-genre <genre_id> --feedback "色面のコントラストをさらに強く"
```
- **API課金ゼロで完走**: `ChatGPT.app` 同梱の公式 `codex exec`（`Logged in using ChatGPT`）を自動検出し、`OPENAI_API_KEY` が未設定または残高切れでも内蔵 `image_gen`（`gpt-image-2`）＋ Vision 審査（`codex exec -i`）へ自動切替して完走します（`OPENAI_API_KEY` / `GEMINI_API_KEY` がある場合もマルチプロバイダで連携）。また Codex 生成時の一時ファイル（`~/.codex/generated_images/<thread_id>`）も最適化直後に自動削除してディスク容量を保護します。
- 生成画像はすべてカードUIに最適な 3:2 横長比率（アイキャッチ `1200x800`、スポット `900x600`）へ `sharp` で高圧縮リサイズされます（基本ジャンルは端まで色が入るフルブリード、絵地図・スケッチ・パステル系のみ自然な紙肌全面表現）。
- Vision 審査が各ジャンルの `rubric` で採点し、基準未満の場合は改善指示を注入して自動リテイクした上で、有効な知見を該当ジャンルの `self_improvement` 枠のみに蓄積します（称号バッジ用の `completion_badge` / `choices[].badge` のみ従来通り和紙余白のある紋章表現を維持）。

### 2. 画像生成サブエージェント（`image-generator`）と和紙ビネット（`#F7F2E6`）一括変換
- `image-generator` サブエージェントで生成した JPEG/PNG を目視検収（`read_file` で文字混入ゼロ・余白良好を確認）した後、以下の `sharp` スムースステップ処理で外周を `#F7F2E6`（和紙色）へ滑らかにフェードさせ、`public/images/<slug>/route-eyecatch.png`（`800x450`）および `spot1.png〜spot5.png`（`560x560`）へ出力する。
```bash
node -e '
const sharp = require("sharp");
const fs = require("fs");
const path = require("path");

function smoothstep(edge0, edge1, x) {
  const t = Math.max(0, Math.min(1, (x - edge0) / (edge1 - edge0)));
  return t * t * (3 - 2 * t);
}

async function processImage(srcPath, destPath, width, height) {
  const { data } = await sharp(srcPath)
    .resize(width, height, { fit: "cover" })
    .ensureAlpha()
    .raw()
    .toBuffer({ resolveWithObject: true });

  const bgR = 0xF7, bgG = 0xF2, bgB = 0xE6;
  const cx = width / 2, cy = height / 2;
  const rx = width * 0.45, ry = height * 0.45;

  for (let y = 0; y < height; y++) {
    const dy = (y - cy) / ry;
    const edgeDistY = Math.min(y, height - 1 - y) / (height * 0.14);
    for (let x = 0; x < width; x++) {
      const dx = (x - cx) / rx;
      const r = Math.sqrt(dx * dx + dy * dy);
      const radialFade = 1 - smoothstep(0.68, 1.0, r);
      const edgeDistX = Math.min(x, width - 1 - x) / (width * 0.14);
      const rectFade = smoothstep(0.0, 1.0, Math.min(edgeDistX, edgeDistY));
      const alpha = Math.min(radialFade, rectFade);
      const idx = (y * width + x) * 4;
      data[idx]     = Math.round(data[idx] * alpha + bgR * (1 - alpha));
      data[idx + 1] = Math.round(data[idx + 1] * alpha + bgG * (1 - alpha));
      data[idx + 2] = Math.round(data[idx + 2] * alpha + bgB * (1 - alpha));
      data[idx + 3] = 255;
    }
  }

  await sharp(data, { raw: { width, height, channels: 4 } })
    .png({ compressionLevel: 9 })
    .toFile(destPath);
}
'
```
- **クォータ上限（`429 RESOURCE_EXHAUSTED`）到達時の自動待機**:
  - `image-generator` がクォータ上限に達した場合は、エラーメッセージ内のリセット時刻（UTC）を確認し、`schedule` ツール（`DurationSeconds`）でリセット時刻＋10秒後までタイマー待機し、起床後に残りの画像生成を自動再開すること（`sleep` コマンドやポーリングは使用しない）。
